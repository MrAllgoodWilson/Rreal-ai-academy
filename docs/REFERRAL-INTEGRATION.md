# Referral foundation — local, disabled; integration acceptance required

Owner requested: after first settled $1 payment show code/link/QR; every20 distinct newly paid referred learners earns$10 project credits and a persistent dashboard notice. This scaffold does not claim live readiness, automatic wallet fulfillment, uniquely human/referral-fraud verification or profitable economics.

## Implemented
- New migration0006 only: opaque referral profiles, immutable signup attribution, first-payment registry, held qualification, repeatable reward cohorts and durable notification acknowledgment.
- Service-only qualifying receipt RPC. Accepts only100 US cents, USD, nonfuture paid timestamp and distinct user/customer/session. Authenticated users cannot qualify their own payment or read raw referred identities/payment records.
- Attribution must occur before first payment; locks learner profile against payment races; first referral wins, no self referral. Codes are visible only after trusted first-paid registration. New payment proof required for existing members; don't backfill from subscription status alone.
- AL explicitly chose immediate rewards after20 qualifying payments. Default hold_days=0; a future hold remains configurable only after a new owner decision. Configurable reviewed policy threshold20/reward1000 cents. Refunded/disputed pending referrals excluded; affected issued rewards flagged for manual review, never silent cash clawback. No recurring renewal counted.
- The trusted paid-event RPC atomically settles the referrer’s milestone immediately; the own authenticated dashboard RPC also reconciles and serializes milestone processing and groups exactly20 previously-unrewarded qualified new members per cohort. Every cohort has a unique milestone and one reward record; duplicate/concurrent dashboard reads cannot grant duplicate entitlements.
- `/api/referrals` gated by `REFERRALS_ENABLED=true`, off by default. GET returns own aggregate counts/rewards plus local QR for first-party signup URL; POST attributes a code or dismisses owned notice. UI component `ReferralPanel` is supplied but not mounted in shared dashboard.
- Reward is a$10 entitlement with `pending_wallet` status, not a fake credit balance. Existing project wallet absent. Legacy video/course balances and migration0004 untouched.

## Atomic project-wallet adapter (0009)

`referral_wallet_control` is disabled with zero funded budget. A real operator must first verify cash already collected and allocate a promo provider-cost reserve **after** payment fees, membership delivery, refund/dispute reserves and minimum contribution. `referral_fund_promo_reserve(verified_source,cost_cents)` is service-only and replay-safe; the source must represent that real approved allocation, never sponsor forecasts, credit face value or fabricated cash. No provider lookup or cash allocation has been performed by this implementation.

After a reviewed feature-allowance mapping version, units and per-reward funded-cost cap are configured, and the existing project-wallet global control is enabled, the0009 insert trigger credits a new earned reward in the same payment→cohort transaction. It locks profile/reserve/reward consistently, deducts the promo reserve, calls `project_wallet_grant` once with `referral:<rewardUUID>`, records immutable cost allocation and marks credited atomically. Funded cap cannot exceed the wallet's configured margin fraction of the reward's retail reference. Units are feature access, not redeemable cash, model tokens or guaranteed provider cost. Disabled/zero/exhausted funding leaves the actual earned entitlement `pending_wallet`, with accurate UI wording. Do not launch promising immediately usable rewards while that state is expected.

Authenticated members can retry only their own earned pending rewards via `referral_credit_own_rewards`; API status reads invoke it. Fraud/dispute review blocks new referral-funded project reservations, including if the referrer's own first receipt was reversed. Already-running provider jobs need manual state/cost reconciliation; do not age-refund. `POST /api/referrals/reconcile` is same-origin and ADMIN_EMAILS-authenticated, bounded20 events/2 requests per minute, retrieves original pending events from Stripe and re-verifies them; attempted is not a fulfillment claim. Missing trusted ownership can remain pending until a real ownership-proof procedure is supplied.

Additional actual SQL checks: `WALLET_MIGRATION_SQL=<reviewed0007file> bash tests/sql/referral-wallet-checks.sh` (or default integrated0007 path). It verifies disabled/unfunded grants stop, approved fixture funding is exactly-once, pending rewards receive one allowance each, reserve exhaustion is honest, forced last-wallet-write failure rolls back reserve/grant/reward together, and retry recovers once. Uses only isolated fixture cash labels; no real funding.
